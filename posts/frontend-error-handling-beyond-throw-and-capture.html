에러 한 건이
알림이 되기까지

TypeError→normalize→classify→enrich→beforeSend→Sentry→Google Chat

Sentry 콘솔 사용법이 아니라, 에러가 우리 코드에서 출발해 알림이 울리기까지 지나는 코드 경로를 따라갑니다. 사내 스터디에서 발표한 덱을 글로 옮겼습니다.

←→ 이동 · F 전체 화면 · 위 막대의 목차·용어 · 슬라이드 아래 자세히에 보충 설명

자세히

예시는 Next.js App Router 앱 두 개입니다. 대화형 서비스 chat-web과 건강 관리 서비스 health-web이 같은 공용 Sentry 패키지를 씁니다. 사내 패키지·앱 이름은 일반화했습니다.

순서: 큰 그림 → 패키지 안(4단계) → 패키지 밖(React Query·서버) → 통합 시뮬레이터 → 알림과 운영.

처음이라면 여기부터 · →로 한 칸씩

쉽게 말하면 · 에러를 응급 환자라고 생각해 보세요. 발견 → 문진 → 중증도 → 차트 → 검문 → 기록 → 호출 순서로 갑니다.

자세히

오늘 볼 전부를 응급실 비유 하나로 먼저 훑습니다. 뒤 슬라이드는 이 칸 하나하나를 확대해서 보는 것입니다.

핵심 두 가지만 기억하면 됩니다: ① 모든 에러가 Sentry까지 가는 건 아니다(중간에 버려진다), ② 모든 기록이 알림이 되는 건 아니다(급한 것만).

에러는 어디서 내리고, 어디까지 가나

쉽게 말하면 · 실선은 우리가 잡아 패키지를 거치는 길, 점선은 아무도 못 잡아 바로 SDK로 가는 길입니다. ✕ 역에서 내리면 Sentry에 안 갑니다.

자세히

위 라인은 브라우저, 아래 라인은 Node 서버입니다. 둘 다 오른쪽 Sentry 역에서 합쳐지고 급한 것만 Google Chat까지 갑니다.

실선(handled): 우리가 잡아서 sentryCaptureException → normalize·classify·enrich → SDK. 이벤트에 isPreProcessed가 붙어 beforeSend는 통과만 합니다.

점선(unhandled): 아무도 못 잡았거나 SDK를 직접 부른 경우. 패키지 단계를 건너뛰고 SDK로 바로 가서 beforeSend ①에서 같은 판단 함수로 분류됩니다.

이 순서로 눌러 보세요: 렌더 TypeError(알림) → 망 단절(classify에서 하차) → 서버 컴포넌트 500(점선, 알림) → SSR 클라이언트 API(필터에서 하차).

자세히

400·403을 warning으로 안 내리는 이유: 잘못된 요청 바디나 권한 배선 실수처럼 프론트 결함이 섞여 있어서 일괄로 내리면 진짜 버그가 알림에서 사라집니다.

caller-opt-out-skip이 1번인 이유: Sentry 자동 계측이 같은 요청을 axios 인터셉터 밖에서 따로 캡처해 우회한 사례가 있었습니다. 그래서 normalize가 config를 직접 읽고 맨 앞에서 판정합니다.

① beforeSendForUnhandledError

isPreProcessed가 있으면 통과. 없으면 normalize·classify해서 level·fingerprint·태그를 쓰고 스킵 판정이면 버립니다. 분류 중 예외가 나도 이벤트는 그대로 넘깁니다.

② 웹뷰 브릿지 노이즈

웹뷰 lifecycle 이벤트(pagehide 등) 리스너 안에서 난 서드파티 SDK의 브릿지 에러만 버립니다. 메시지만 보고 거르면 우리 브릿지 에러까지 묻히기 때문입니다.

③ 서드파티

third_party_code 태그가 있을 때만. 노이즈면 버리고, 확실히 남의 코드면 제목을 ThirdPartyError (…)로. 우리 API 에러·위치 없는 프레임·우리 번들 청크는 손대지 않습니다(모르면 우리 것). 예외 하나: Sentry가 감싼 콜백(setTimeout·addEventListener)인데 남은 프레임이 Sentry wrap뿐이면 콜백 자체가 위치 없는 주입 스크립트라 버립니다.

④ 앱 beforeSend

공용 판정 뒤라 앱이 최종 결정. 예를 들어 health-web은 인앱 브라우저 브릿지 노이즈를 info로 내립니다(기록은 남기고 알림만 끔).

로컬 콘솔

NODE_ENV=development면 보낼 내용을 console.error('[will be sent to Sentry]', …)로 찍고 버립니다.

자세히

순서가 곧 우선순위. 하나라도 null이면 거기서 끝. 앱 정책이 맨 뒤라 최종 결정권을 가집니다.

health-web이 인앱 브라우저 노이즈를 버리지 않고 info로 내리는 이유: info는 "기록은 남기고 알림만 끄는" 표준 수단입니다. 급증하면 볼 수 있어야 합니다.

훅마다 Sentry까지 가는 길이 다르다

쉽게 말하면 · 같은 API 실패라도 어떤 훅을 썼느냐에 따라 Sentry에 가기도, 안 가기도 합니다.

용어
  • throwOnError · 에러를 ErrorBoundary로 던질지 정하는 옵션. 앱 기본값이 이 안에서 캡처한다
  • meta · 쿼리·뮤테이션에 붙이는 옵션 객체 (sentryOn409: false 등)
  • 앱 게이트 · meta를 보고 보고 여부를 거르는 함수
  • Dedupe · 직전과 같은 이벤트를 SDK가 버리는 기능
요청 바디가 Sentry에 남는다. SDK가 axios config.data를 context로 그대로 싣습니다. 예: 탈퇴 실패 시 사용자가 쓴 사유.
자세히

재시도는 셋 다 같음: 5xx·망 단절·타임아웃(408)만 2회, 나머지 4xx·취소는 바로 실패. 다른 건 마지막 실패를 누가 받느냐.

왜 게이트가 패키지 밖에: data-access는 Sentry를 모릅니다. createAppQueryClient는 captureException을 주입받고, 재시도(retryOn404)와 보고(sentryOn404)를 같은 meta에서 정하려고 게이트를 쿼리 쪽에 뒀습니다. 대가로 끄는 어휘가 두 벌(axios config 400/403/404, meta 400/404/409/429/503).

suspense 우회는 TanStack 버그가 아니라 캡처를 throwOnError 안에 둔 결과. queryCache.onError로 옮기면 suspense·refetch 실패도 게이트를 탑니다(대신 바운더리 재캡처 중복 정리 필요).

요청 바디: extraErrorDataIntegration이 에러 객체 필드를 context로 펼치며 axios config.data(바디 JSON 문자열)를 싣습니다. mutation.variables context는 기본 깊이 3에서 [Object]로 잘립니다.

서버 컴포넌트가 API를 직접 부름

동의 이력 화면(서버 컴포넌트). 서버엔 React Query도 재시도도 없어서 한 번 실패로 ServerFetchError(status·url·method·payload)가 납니다.

Next.js → onRequestError

렌더가 실패하면 instrumentation.ts가 내보낸 Sentry.captureRequestError를 부릅니다(unhandled).

beforeSend ①

kind server-fetch, 5xx → error. 제목을 엔드포인트로 바꿉니다. 서버 체인은 ①과 로컬 콘솔 두 단계뿐.

서버 이슈

원인(엔드포인트)이 보이는 쪽. user 필드는 비지만 SDK 기본값(requestData의 cookies: true) 때문에 요청 쿠키(guid 등)는 실립니다. ServerFetchError 필드도 context로 실립니다. consent-history도 하이픈이라 {param}.

배포 빌드(dev·stg·prd)는 메시지를 지운다

Next.js가 에러를 브라우저로 넘길 때 원래 메시지를 지우고 digest(서버 에러와 짝을 맞추는 해시)만 남깁니다.

error.tsx가 받는다

에러 화면은 그대로 보여 줍니다. 보고는 공용 captureBoundaryError로 하고, 바운더리 공통 처리(user 세팅 등)도 그대로 돕니다.

digest가 있으면 보내지 않는다

digest는 서버 렌더 에러에만 붙습니다. 원본은 ①~④에서 이미 보고했으니 건너뜁니다. 예전엔 여기서 메시지 없는 An error occurred in the Server Components render가 error로 따로 올라가, 서버 401(warning)까지 알림을 울렸습니다.

// error.tsx · global-error.tsx
captureBoundaryError(error) // digest 있으면 return

서버 이슈 하나만 본다

원인(엔드포인트)과 빈도는 서버 이슈에 있습니다. 서버 이벤트엔 user가 비어 있어 영향 사용자 수는 정확히 나오지 않습니다. 클라이언트에서 난 렌더 에러는 digest가 없어 지금처럼 바운더리가 보고합니다.

Route Handler가 실패를 응답으로 바꿈

Next.js엔 정상 응답이라 onRequestError가 안 울림 → 직접 sentryCaptureException. 외부 API가 닫은 keep-alive 소켓 끊김(UND_ERR_SOCKET)은 공용 클라이언트가 조회 요청만 1회 다시 보냅니다.

SSR 중 클라이언트 전용 API

SsrSkippedApiCallError → 서버 ignoreErrors가 버림. 클라이언트에서만 쿼리를 띄우는 게이트 컴포넌트로 애초에 막기도 합니다.

서버 요청 401

dev·stg·로컬 + 테스트 계정 env + 재시도 대상 코드(401002·401016·코드 없음)일 때만 한 번 다시 부릅니다(실제 쿠키 갱신은 로컬만). prd는 바로 렌더 실패 → 서버 이벤트는 warning. 브라우저는 digest라 보고하지 않으니 알림도 가지 않습니다.

자세히

운영 관점: 서버 이슈 하나만 남습니다. 예전엔 브라우저 error.tsx가 digest만 남은 사본을 따로 보내, 원인 없는 error 이슈가 하나 더 생겼습니다. 서버가 401을 warning으로 낮춰도 이 사본 때문에 알림이 울렸습니다.

잃는 것: 서버 이벤트엔 user가 없어 영향 사용자 수를 바로 볼 수 없습니다. 필요하면 서버 쪽 scope에 user를 심는 방향으로.

자세히

릴레이가 environment(staging·production)와 level(error 이상)로 거릅니다. 규칙이 언제 발동하는지(새 이슈·회귀 등)는 Sentry 알림 규칙 설정을 따릅니다. pre-production은 릴레이 조건에 없습니다.

끄기 vs 낮추기: 404·409·429는 이미 warning이라 끄면 알림은 그대로고 빈도만 잃습니다. React Query 경로는 호출부가 level을 넘길 수 없어서 앱 beforeSend에서 경로·메시지 단위로 내립니다.

0건: 게이트웨이가 CORS 헤더 없이 502를 주거나 서버가 응답 없이 멈추면 브라우저엔 Network Error. queryFn에서 .catch(() => null)로 삼킨 쿼리(브리핑·추천 질문 등)는 API가 다 죽어도 0건.

자주 받는 질문: "401이 쏟아지면?" 401은 warning이고 일부 코드는 앱 게이트의 401 정책이 캡처하지 않아 알림 없음. 이슈 빈도로 봅니다.

자세히

Sentry에는 Google Chat 기본 연동이 없어서 Sentry 웹훅을 Apps Script Web App으로 받아 Google Chat 웹훅으로 넘깁니다. 앞 슬라이드의 "stg·prd에서 error 이상만" 조건은 이 릴레이가 거릅니다. 환경마다 채널 웹훅을 따로 둡니다.

순서 역전은 세 겹으로 처리합니다. triggered 때 이슈 ID별 environment를 1시간 캐시해 두고 assigned 때 꺼내 씁니다. 캐시가 아직 없으면 assigned를 잠시 보류했다가 triggered가 스레드를 만든 뒤 답글로 보냅니다. 그래도 없으면 Sentry API로 최신 이벤트를 조회해 environment를 알아냅니다. 확인과 보류 등록은 락으로 묶어 그 사이에 triggered가 지나가 보류분이 고아가 되지 않게 했습니다.

멘션은 Sentry 담당자 이메일을 Chat 사용자 ID로 바꾸는 표로 합니다. 매핑이 없으면 이름만 굵게 씁니다.

레벨은 받아온 뒤 거른다

이슈 검색의 level:은 이슈에 포함된 과거 이벤트까지 봅니다. info로 낮춰 알림을 끈 이슈가 다시 걸려 나오므로, 표시 레벨을 릴레이와 같은 기준(error 이상)으로 직접 거릅니다.

"어제"는 KST 자정 기준

statsPeriod=14d는 UTC 일자로 잘려 KST 오전 리포트의 "어제"와 하루 어긋납니다. 조회 구간을 KST 자정 경계로 직접 맞춥니다.

조용히 죽지 않는다

실패하면 사유를 같은 채널에 보냅니다. 리포트가 안 오는 걸 아무도 눈치채지 못하는 게 가장 위험합니다.

자세히

릴레이가 "이슈가 생긴 순간"을 알린다면, 데일리 리포트는 "쌓여 있는 미해결"을 리마인드합니다. 같은 Apps Script 프로젝트에 붙였고 Google Sheets에 일자별로 아카이브합니다. 같은 날짜 행이 있으면 덮어써서 다시 돌려도 아카이브가 오염되지 않습니다.

events-stats의 top events 집계에서 orderby=-count()를 빼면 가장 큰 프로젝트가 Other 버킷으로 밀려 사라집니다. Google Chat 메시지는 4096자가 한도라, 넘으면 담당자당 이슈를 3건에서 1건으로 줄여 다시 렌더합니다. 시간 트리거는 정시가 아니라 10~11시 구간에 돌고, 주말은 함수 안에서 건너뜁니다. 설치할 때는 발송·기록 없이 수집과 렌더만 검증하는 자체 점검 함수를 먼저 돌립니다.

// 대시보드 정의에서 담당자·제외 필터를 읽는다 (하드코딩 대신 단일 출처)
for (const widget of dashboard.widgets || []) {
  for (const query of widget.queries || []) {
    const cond = query.conditions || ''
    for (const token of cond.match(/assigned:(\S+@\S+)/g) || []) {
      const email = token.slice('assigned:'.length)
      if (!assignees.includes(email)) assignees.push(email)
    }
  }
}

보고하는 코드를 쓰기 전에

쉽게 말하면 · 내가 에러를 보고하는 코드를 쓸 때 확인할 6가지. 눌러서 하나씩 체크하세요.

쿼리·뮤테이션·ErrorBoundary·error.tsx가 이미 보냅니다(서버 렌더 에러는 onRequestError가). catch에서 또 보내면 두 번째는 SDK가 대개 버려서 거기 붙인 tags·level이 조용히 사라집니다.

실패를 응답·리다이렉트·토스트·null로 바꾸면 Sentry는 모릅니다.

import { sentryCaptureException } from '@/lib/sentry'

sentryCaptureException(error, { tags: { boundary: 'checkout', gate: 'outbound' } })

뮤테이션 meta가 가장 확실합니다. useQuery meta는 바운더리가 다시 보고하고 suspense엔 무효라 쿼리는 axios config(sentryOn400/403/404)로. 503은 앱 beforeSend로만.

useRecalculateScore({
  mutation: { meta: { sentryOn409: false } },
})

결제·서명은 level: 'fatal', 기록만이면 'warning'. 도메인 지식이라 패키지가 대신 못 합니다. 스킵 판정(망 단절 등)은 명시한 level보다 우선.

태그 = 값 종류가 몇 개뿐인 검색용(feature, boundary). ID처럼 계속 달라지는 값은 context. 건강 정보·개인정보는 어디에도 넣지 않고 민감한 바디를 보내는 요청은 실패 시 바디가 실린다는 걸 기억합니다.

Sentry.captureException보다 sentryCaptureException. 래퍼를 써야 내가 넘긴 level·fingerprint가 그대로 갑니다. error.tsx·global-error.tsx에선 digest를 걸러 주는 captureBoundaryError.

자세히

가장 흔한 실수는 첫 번째. 이미 React Query가 보내는 에러를 catch에서 태그를 붙여 또 보내면, 태그 붙은 쪽이 사라집니다.

입구마다 길이 다르다

useQuery · useSuspenseQuery · useMutation · 서버 컴포넌트

throw하고 captureException을 부르는 데서 끝나지 않습니다. 에러 한 건이 어느 길로 들어와 어디서 버려지고 무엇이 알림이 되는지 알아야 알림을 믿을 수 있습니다.

자세히

01: 앱 게이트·normalize(axios config)·classify·앱 beforeSend. 새 예외는 가장 바깥(앱)에. 02: stg·prd에서 error 이상만. 끄기와 낮추기를 구분. 03: useQuery·useSuspenseQuery·useMutation·서버 컴포넌트는 각자 다른 곳에서 보고됩니다.

자주 받는 질문: "백엔드가 통째로 죽으면?" 브라우저: 5xx는 오지만 CORS 실패·응답 없는 멈춤은 0건. 서버 컴포넌트: 망 단절도 status 없는 ServerFetchError라 default error로 알림이 갑니다. "suspense 쿼리에서 400 끄려면?" axios config의 sentryOn400(503은 앱 beforeSend로만). "RSC 장애면 알림 두 번?" 아니요. 서버 이슈 하나만 울립니다(브라우저 error.tsx는 digest라 생략).
